# EMCIA Gestion — 2026.11.14.2

## Atomic state saving

The new invoker RPCs `emcia_load_state_v2` and `emcia_save_state_v2` preserve the existing RLS. Loading returns a consistent operational/financial snapshot. Saving locks records in the same order, checks both revisions before any write, and commits both updates in one transaction. A conflict rolls back the operation. Secretary requests contain only the operational payload; a financial payload from either secretary role is rejected by the server. There is no sequential PATCH fallback in the new application. Backup restoration uses the same transaction.

The schema migration adds two functions and their grants; it does not rewrite business records. The old app remains compatible at the table level during deployment. Old open tabs should be reopened to load the new application.

## Session accounting

- Individual balances are derived from completed lessons and actual session receipts, using cents for allocation and rounding.
- Receipts fund the learner's oldest outstanding lessons in the same group. Learners' balances remain independent.
- Unused funds stay as learner credit. They are included in actual cash receipts, but excluded from earned teacher/institute shares until the corresponding lesson is completed.
- Teacher and institute shares are recognized in the later month of lesson delivery and collection. Partial receipts recognize proportional shares; rounding cumulative shares prevents cent drift across receipts.
- Teacher-only, institute-only, equal shared and custom discounts use the configured discount terms for the lesson month. Newly recorded lessons store their learner unit price/discount. Teacher percentage and missing historical custom-discount components use the existing group/enrollment configuration, consistent with the current monthly model; historical rate locking is not introduced by this release.
- Explicitly absent/excused flexible lessons are excluded. A legacy day-only entry is counted at most once and is not duplicated with flexible lessons on the same day. Ambiguous historical day-only data cannot recover multiple actual lesson times.
- Budget, dashboard, monthly/financial/admin reports, teacher statements and remuneration settlement include session accounting. Operational screens show the learner's unpaid lessons and advance credit separately from monthly tuition arrears. Teacher statements do not expose the institute's share.
- Financial receipt/recognition rows are projections, not extra records stored in `p`; calculations therefore do not duplicate the original receipts or change existing monthly payments.

## Verification

- Database tests use synthetic rows inside transactions ending in ROLLBACK. Director save/conflict/rollback, accountant finance access, and both secretary roles' operational access and denied financial access passed.
- DOM/authentication/sync tests mock all network requests. They cover independent attendance, payment editing and reload, duplicate receipts, strict dates, stable financial IDs and atomic rejection without changing either remote payload.
- Financial cases include advances across months, late/partial receipts, all four discount bearers, two lessons on one day, independent learner balances, deleted receipts, and teacher-report privacy.
- No real employee password or production session was used. Real-device visual acceptance remains distinct from these automated checks.
